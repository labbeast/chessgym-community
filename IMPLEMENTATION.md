# ChessGym V1 implementation contract

## Personal weekly training programs

`training_programs.py` owns versioned definitions, resource identities, personal templates, activation and weekly snapshots. `training_activity.py` owns execution contexts, attribution, accepted-event credits, manual corrections and aggregates. `training_program_api.py` exposes authenticated `/api/training` routes. App startup calls the additive `training_programs.init_schema(conn)` after native schemas exist; helpers participate in the caller's transaction and never commit it themselves. All new tables live in the personal SQLite database and are included in its existing backups.

Program writes compare expected revisions and retain mutation receipts. Retry the same payload and ID after an uncertain response; receipt lookup precedes revision validation. `GET /state` and other reads never create a week. `POST /weeks/current` applies any due activation and ensures a weekly snapshot atomically. Edits target future weeks unless explicitly applied to the current week. The snapshot stores the study-day rules. Attribution across weeks requires the same program, block ID, activity, resource generation and unit; incompatible work remains visible outside current targets.

Native review creation accepts `training_run_id` for a single-base session or a daily session restricted to one base. Grading records credits in its native transaction after receipt validation. Manual mastery produces no worked answer. Reading attaches the context before its first write and credits accepted native increments by receipt; several visits can belong to one run. Run completion requires actual work and counts once. A reading-game confirmation adds quantity only. Free work can be assigned without copying its credits, and explicit compatible episodes can count a session. Recording dates determine the study week; no historical active intervals are fabricated.

The SPA route `#/training-plan` mounts `static/training-plan.js` with Today as the default. `training-program.js` implements the composer and models; `training-plan-launch.js` retains native launch and run-mutation receipts; `training-session-bar.js` connects native views to pause, completion and return actions. Program drafts use the account-and-epoch workspace. Other native training tools use training_native.py and static/training-native.js for durable program context, accepted-fact credits, cumulative high-water marks and explicit completion. The server remains authoritative for progress; DOM callbacks do not award credit.

Daily effort and the seven study days are aggregated from the same dated credits as the weekly totals, including manual corrections and unmatched former blocks. Nullable `attempts` counters in `training_activity_credits` and `training_native_sources` keep submitted attempts separate from goal units and use cumulative high-water marks. Migration recovers only established review/position counts; unknown legacy guess counts are baselined. Unique matching free work is assigned by default unless explicitly disabled. Accepted native writes prepare the current week and pending activation before matching; reads remain side-effect free. Automatically assigned free work can explicitly complete an episode without copying duration or attempts.

Core tests live in `tests/test_training_programs.py`, `test_training_native.py`, `test_training_native_ui.py`, `test_training_daily_progress.py`, `test_training_plan_ui.py` and `test_training_plan_launch.py`. `scripts/test_training_plan_browser.py` runs an isolated local server and browser profile, checks composer-to-native journeys, automatic free-work attribution, daily/weekly counters after reload, responsive French/English views, and verifies that source PGNs remain unchanged.

## Computer games

`computer_api.py` provides authenticated `/api/computer/opponents`, `/position`, `/move` and `/timeout`. Every position is replayed from `initial_fen` plus legal UCI `history`, with optional expected-FEN validation. Responses include a detached PGN document, current path, legal moves and terminal status. This stateless service never writes to a library or review record. Claimable draws end the game automatically, matching existing engine play behavior.

Stockfish uses its existing bounded play lane and skill 0–20. `maia_engine.py` shares that lane's gate and resource lease, runs the official Maia 3 UCI module in a separate CPU-only Python environment with one compute thread, and closes it on application shutdown. A single process and loaded checkpoint are reused across rating changes. Explicit Elo, Temperature=1, TopP=1 and MultiPV=1 settings produce sampled human-style moves; the complete supplied legal history is sent with `--use-uci-history`. Checkpoints are local, model loading is tensor-only, and Hugging Face runs offline. Maia's prediction scores are not exposed as Stockfish evaluations. The provider identifier remains `maia` so retained sessions keep working. The installer pins source/model downloads and preserves licenses/provenance under `engines/maia3/`; the original Maia-1 directory is not modified. The UI offers rating targets 600–2600 with Lichess as a reference, not calibrated engine Elo.

`static/computer-play.js` owns a separate game state and an abortable view. `app.js` persists the active game to the account-owned `computer` workspace slot through `WorkspaceStore`, which writes synchronously to local storage and synchronizes by CAS. `computer-workspace.js` projects the active session independently of pending setup options and retains no empty setup drafts. The session freezes its engine configuration. A pending human move is retained as an intent, revalidated once on resume, and cleared on confirmation or explicit cancellation; a pending computer reply is derived from the side to move. Reload/browser-close recovery uses the same view loader, and conflicts retain both versions until explicitly resolved. No library-entry route is called for retention. Launching from analysis copies the path to the selected position, leaving the existing document and cursor intact. A library entry is created only by an explicit copy/save or by the separately enabled computer-mode automatic-copy preference. Browser tests run via `scripts/test_computer_play_browser.py` with temporary data and verify the source PGN remains byte-for-byte unchanged.


`computer_history.py` and `computer_history_api.py` own account-scoped computer history independently of the bounded workspace slot. `PUT /api/computer/games/{id}` legally replays the supplied session, regenerates its PGN and uses integer CAS revisions. A stable `mutation_id` plus the original payload hash makes a lost-response retry idempotent; reusing the ID for different data fails. Expensive replay and PGN generation run before the SQLite writer transaction. The mode's settings and copy links live in separate personal tables. Automatic copies run only at a new finish or to retry a recorded copy failure; they never rewrite an existing library entry, and a deleted automatic copy is not recreated without an explicit copy action. Reference destinations are rejected. Personal SQLite backups include all these records.

`static/computer-history-store.js` owns a per-account, per-workspace-epoch local outbox and serializes history writes independently of current-page navigation. A new game or replay first preserves the previous session. `static/computer-history.js` supplies the paginated archive, detached read-only board and optional-copy settings; inspecting an archive never launches the engine. Only the last legacy workspace game is recoverable, not older unsaved games already replaced before the feature existed.

`static/computer-clock.js` owns remaining milliseconds and increment checkpoints indexed by absolute history ply. It never persists a wall-clock deadline: closing the browser, hiding its tab or leaving the board pauses play, and loading a timed session requires an explicit resume. `computer-play.js` cancels pending engine work on pause and retains unconfirmed human intent in the workspace only. Timeout adjudication validates the side to move and uses the board's opponent-material test; a position already terminal keeps its original result. Server PGNs include `TimeControl`, `Termination` and `[%clk]` only for plies played after the session's analysis-position baseline.

## Puzzle ratings

`puzzle_rating.py` implements the Glicko-2 equations with the revised Illinois volatility solver and Lichess parameters (RD 500 initially, volatility 0.09, tau 0.75, RD bounds 45–500, maximum volatility 0.1 and maximum raw change 700). Both classic puzzles and the two blindfold profiles use this calculator. Classic puzzles use the bank's rating deviation; blindfold exercises persist that deviation beside their local visual/tactical difficulty. Lichess's selected-theme and provisional-opponent weights apply after the calculation. Standard mixed puzzles are not weighted by their ordinary tags. The imported bank remains read-only; local rating bounds remain 100–4000 for classic and 500–3000 for blindfold.

Profile migrations add `rating_deviation`, `volatility` and `last_rated_at` without rewriting existing ratings, counts, settings or history. Legacy profiles begin with high uncertainty to recalibrate quickly. Each accepted grade updates all four values in the existing grading transaction. Classic attempts retain their post-grade RD and selected themes for consistent replay. Existing request receipts, first-error grading, blindfold eligibility and grade uniqueness still prevent duplicate credit. Non-rated practice and Storm do not change these parameters. Backups retain the complete state in the personal database.

Public profiles preview time-driven RD growth at 0.21436 periods/day without writes. A rating is provisional while RD is at least 110, independently of attempt count. The UI no longer implies that exactly 20 puzzles establish a rating. The formula is checked against Glickman's published three-opponent example, plus convergence, bounds, inactivity, migration, mode isolation and request replay regressions.

## Blindfold puzzle reconstruction

New opening/positions sessions set `reconstruct_after=true` by default, including rated puzzles, but the option can be disabled. The optional second stage is represented in existing JSON state, without another database table. The final accepted move stores `solve_result`, `reconstruction_started_at` and the actual final `target_fen`, then returns `phase=reconstruct` with `finished=false`. No target FEN, PGN document, prompt or played-move list is returned during this phase. `/position` grades the submitted piece map and retains both `solve_*` and `reconstruction_*` result/time fields. Puzzle success and the rating result depend only on a complete error-free solution; reconstruction accuracy is a secondary statistic. Skipping, revealing or replacing the exercise after the solution preserves its result and records `reconstruction_skipped`; revealing or abandoning before completing the solution remains a failure. Grading still occurs once when the session finishes, and existing rating events and history are not recalculated. Personal-game reconstruction retains its own exact-position success rule. Account ownership, first-submission idempotence and untouched source PGNs remain enforced. Missing flags identify older sessions and preserve their single-stage behavior. An accepted alternative immediate mate retains its actually played line and target, rather than substituting the puzzle's original continuation.

## Color training

`color_training.py` owns authenticated `/api/skills/color` sessions in `color_sessions`. The first accepted answer establishes the server deadline for 30 or 60 seconds. Every response advances to a different square; parity is fixed to standard square coordinates (a1 is dark), independently of board orientation and theme. Per-question index and nonce validate responses, and the last exact response receipt makes a lost-response retry idempotent without adding another score. GET/history/finish settle expired sessions consistently. Starting another session abandons an unfinished attempt unless its deadline has already elapsed.

The server calculates `record_eligible` from completed duration, at least one answer and `errors == 0`; it never infers eligibility from the rounded display percentage. Personal bests are queried separately for 30 and 60 seconds. All routes filter by account, and personal backups include the session table. `static/color-training.js` renders square prompts, left/right keyboard shortcuts, feedback and history, using the server deadline and score rather than trusting submitted totals. This timed drill does not use the paused practice clocks from computer games.

## Module boundaries after the October 2026 refactor

`app.py` composes routers, middleware and startup/shutdown. Study-game routes live in `entries_api.py`, free-board routes in `board_api.py`, reading routes in `reading_api.py`, and draft routes in `workspace_api.py`. They share `entry_service.py` for explicit saves, revisions and undo history; `entry_content.py` supplies the same content fingerprint to the editor and catalogue. Domain modules must not import `app.py`. Existing application-level aliases remain for compatibility.

The application lifespan registers service cleanup before starting background work. Its exit stack stops jobs, query preparation, reference imports and engine lanes in dependency order, retaining the offline-restore guard until the end. A partial startup or one failed cleanup does not skip the remaining callbacks. `tests/test_app_lifecycle.py` covers these failure paths.

`engine_output.py` owns the bounded stdout-reader queue shared by background Stockfish, interactive analysis and Maia. Each lane retains ownership of its subprocess, protocol, cancellation and resource budget. `static/identifiers.js` supplies record and retry-receipt UUIDs, including HTTP LAN contexts without `crypto.randomUUID`; these identifiers are not authentication secrets.

Training summaries and activation share a request-local resource index, rebuilt on the next call so settings changes remain visible. Reading summaries load bookmarks in one batch and reuse the existing pure projection without writing reconciled progress. SQL-budget regressions cover both paths.

`pgnlib.game_payload` walks the PGN tree with one board and a stack, restoring board and clock state when leaving each branch. It preserves paths, comments, NAGs, null moves and clock estimates. `reading_progress` uses one pure bookmark projection for both its read-only catalogue summaries and transactional updates.

`game_metadata.py` defines PGN identity serialization, ratings and cadence classification shared by study collections and large reference archives. Its identity bytes are a compatibility contract for already imported games. `game_filters.GameFilter` validates one population and exposes equivalent in-memory matching and parameterized SQL predicates; missing ratings and unknown cadences keep their existing meaning.

`training.py` retains review persistence and transactional grading. `review_schedule.py` owns pure grade/interval rules with an explicit clock; review preferences are read together. `engine_api.py` owns Stockfish HTTP validation and streaming lifecycle, while `engine.py` and `interactive_engine.py` retain their process lanes. `engine_variations.py` shares legal variation serialization with explicit policies for history and incomplete lines.

On the client, explorer rendering, source settings and credentials are separate modules. `review-resume.js` reconciles an interrupted session after content edits, `board-geometry.js` holds board coordinates and SVG overlays, `settings-page.js` composes global settings, and `catalog-request.js` owns cancellable catalogue preparation retries. These helpers do not own application navigation or saved PGNs.

Refactors preserve HTTP paths and authentication, explicit-save semantics, review receipts, archive identity, and resumable import checkpoints. Validate backend/unit/UI contracts with `python -m pytest -q`; the isolated browser runners under `scripts/test_*_browser.py` exercise complete user journeys without using the personal database.

`scripts/test_learning_changes.py --full` isolates application data and temporary files for the complete suite. It clears inherited puzzle-bank configuration so per-test data directories remain authoritative; the puzzle and skill browser runners explicitly select their own fixture bank. `tests/test_runner_puzzle_isolation.py` checks that seeding cannot change an inherited bank.

Performance/settings iteration: personal entry summaries use a derived catalogue with server pagination; the legacy unpaged endpoint remains compatible. Large-reference query cancellation and bounded/persistent caches must never turn partial results into zero matches. Resource profiles share CPU/hash budgets between both engine lanes and imports, and defer changes while work is active. Generic defaults remain modest; explicit launcher imports are preserved unless overridden by a saved profile.

Review sessions persist ordered identifiers and fetch solutions in pages. Session records are retained for resuming; no automatic purge is currently applied. `study_day` defines the activity/calendar and maintenance boundary; `review_session_defaults` defines optional goals, and per-base `new_order` applies to new exercises while opening probability ordering retains priority. The preference service serializes frontend account writes. Device startup choices stay local; a restored database changes `workspace_epoch` to isolate old browser drafts.

Backup automation uses `backup_service` and authenticated `backup_api`. Fresh installs default disabled with suggested values of 24 hours and 7 copies. A short independent scheduler launches a bounded background backup; rotation only removes owned automatic files after successful integrity verification. Offline restoration requires the application lock, retains a rollback snapshot, clears sessions and preserves separately managed reference stores. It never restores a production database from an HTTP request. The Windows launcher and Python CLI provide the restore path.

## Personal games, background reports and exercises

Modules: sync.py (account settings, import and scheduler), sync_remote.py (public API adapter), jobs.py (persistent worker), game_analysis.py (Stockfish reports and exercises), static/played-games.js and played-games.css (French UI). app.py initializes their schemas and authenticated routers, registers the sync/analyse handlers and starts one worker during lifespan; shutdown requests a bounded graceful stop. No actual player account, imported game or demonstration data is configured automatically.

## Large reference databases

`reference_store.py` implements a separate SQLite store for each reference base under `data/references/<storage_key>.sqlite3`. The primary study database keeps only the library/folder metadata and source/import configuration. Reference imports do not populate `entries`, training cards or analysis jobs. Reference content is immutable through the study-editing endpoints; opening a reference game creates a free analysis and saving it creates an ordinary study entry.

The importer reads PGN and `.pgn.zst` incrementally, preserving each PGN as a compressed record. UTF-8 is the default; Windows-1252 and Latin-1 can be explicitly selected for legacy exports and are transcoded to UTF-8 in storage. Invalid byte sequences are rejected rather than silently replaced or retried under a guessed encoding. The original source file is unchanged. It validates the complete game, including variations, but indexes only mainline positions. Metadata columns and SQLite indexes support server-side pagination, date/player/rating sorting and rating/cadence filtering without parsing PGNs on list requests. Both players must meet a supplied rating range; the cadence is derived from `TimeControl`, and unknown or unsupported controls are not silently classified as rapid.

Position keys encode the six piece-type bitboards, White occupancy, side, orthodox castling rights and effective legal en-passant square in an exact binary representation. They are not probabilistic hashes and ignore halfmove/fullmove counters. A game contributes at most one occurrence per position: its first outgoing occurrence, or its terminal position if that position was not visited earlier. The explorer aggregates games and outcomes, including unknown results separately. Repetitions do not inflate statistics. Position search returns the mainline ply used to reopen the complete game at that position; secondary PGN branches remain available to read but are outside the reference index in this version.

`import_file(store, source, max_games=..., batch_size=250, cancelled=..., progress=...)` commits games, position rows and the source checkpoint together. The maximum counts records processed during that call, including rejected records and duplicates. A pause or limit leaves committed games queryable. Plain PGNs resume by seeking to the committed byte offset. Zstandard sources resume by streaming and discarding the decompressed prefix before that checkpoint, without reparsing or reinserting it; this can take time for a large compressed source. Source path, size and modification time identify the current import. If those change, a new pass begins and semantic deduplication applies against existing games. Deduplication compares the compressed identity payload after its digest lookup to avoid hash-collision assumptions. Rejection details are bounded; malformed records never enter the position index.

`reference_library.py` exposes authenticated `/api/reference-bases` creation, import status, pause/resume, paginated games, complete-game reads and streamed PGN export. `reference_worker.py` runs the import in a separate hidden Python process, with one reference import at a time and bounded SQLite caches. It does not hold the study database open during parsing or start Stockfish. `static/reference-library.js` renders the library table and import controls, guards stale asynchronous responses and releases requests/polling on navigation. Reference bases stay in the existing folder tree and are offered as local explorer sources; study-specific actions continue to target ordinary bases.

`reference_actions.py` adds explicit selection operations through `POST /api/reference-bases/{id}/games/batch`: duplicate into the same reference or another reference/study base, move to another base, and delete. Only selected PGNs are decoded; position removals use their indexed position keys. Active imports and stale selections are rejected. Game counts, position counts and a mutation revision change with the operation; queries include that revision so prior cached results cannot hide edits. Deleted game IDs remain reserved when imports resume. The reference list offers individual and visible-page selection, cross-page selection counts, row menus and confirmation dialogs; selection actions do not enable study-only editing or reviews on references.

Reference imports use up to four parsing processes automatically, reserving two logical processors where possible; `CHESSGYM_IMPORT_WORKERS=1..16` overrides this at server startup (`auto` is the default). Direct `reference_store.import_file(..., workers=1)` calls retain sequential behavior. `reference_parallel.py` parses, validates, compresses and prepares the position index in spawned workers; only the coordinator writes SQLite and commits results/checkpoints in exact source order. Pending work is limited to two batches per parser and 32 MiB of raw input, with 64-record/1 MiB batches and the existing single-record limit. The import writer uses a 128 MiB SQLite page cache; readers retain their small caches. Cancellation discards unread prepared work and resumes at the committed prefix.
